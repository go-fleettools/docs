modfloor

The Go toolchain floor a module declares, against the floor a fix requires. Repository → Latest tag: v0.7.0; this page is written from its README at that tag. v0.3.0 added the modfloor pseudo subcommand, below; v0.4.0 splits the exposure by whether a consumer can reach it, below; v0.5.0 adds --baseline, below, and corrects the population every earlier figure was counted over; v0.6.0 costs the campaign in pull requests, below; v0.7.0 groups it by the floor each module declares and stops the ratchet calling population growth a regression.

A repository can be green, released and built with a patched toolchain while still shipping a vulnerable floor to everyone downstream. Three pins decide three different things: go-version: in a workflow builds the artefacts; the toolchain recorded in a binary says what one installed executable was built with; and the go directive in the published go.mod is what a consumer honours under GOTOOLCHAIN=local. Only the third is the exposure, and no green check looks at it.

Install and usage 

GOBIN=~/.local/bin go install github.com/go-fleettools/modfloor@latest
modfloor --dir ~/Documents/VCS/GIT/localhost --owners 'go-*' --floor 1.27.3
modfloor --bins ~/.local/bin --floor 1.27.3
modfloor --floor 1.27.3 github.com/go-fleettools/fleettools

Verdicts, kept apart because they call for different work:

VerdictMeaning
okthe go directive is at or above the floor
toolchainthe directive is below it, but a toolchain line pins higher: the build fails closed under GOTOOLCHAIN=local. Not an exposure
BELOWthe directive is below the floor and nothing pins higher: the exposure
no-gono go directive at all
unreadablea directive that is not a Go version

Exit status: 0 clean, 1 at least one module exposed, 2 the measurement could not be made.

What it reads, and what it refuses

It reads the published go.mod from proxy.golang.org, where a consumer reads it too, not the working tree (which may hold an unreleased fix) and not a workflow. It spends no GitHub API budget and needs no credential. --owners is a declared population, and every number in the report is about that set; a module in no git work tree, or under another owner, is set aside and counted. A measurement that found nothing refuses rather than reporting a clean fleet.

⛔ And being in our work tree does not make the module ours — the half that was missing until v0.5.0. remote.origin.url answers “whose repository is this”, not “whose module is this”, and a repository that carries other projects’ sources put 540 of them into this fleet’s figures. A module whose path is not the repository’s own path — github.com/<owner>/<name>, or a subdirectory or /v2 of it — is set aside as published by another project.

Two traps it encodes: go/version accepts go27.2 (a typo that compares above every real version), so the floor is validated; and modfile.ParseLax does not fill File.Toolchain, so the directive is recovered from the syntax tree.

The exposure, split by who can reach it

One number over both populations cannot be prioritised. A module on the proxy imposes its floor on everyone who runs go install; one that was never published imposes it only on somebody building from a clone. Those are a campaign and some housekeeping, and until v0.4.0 the report added them together. A third line counts the modules whose working tree is already at the floor and whose published module is not — the fixed locally, UNRELEASED state, where the pull request is merged and the work is not finished, because the consumer reads the published go.mod and not the branch. This tool exists because those two differ, so that state is counted by name instead of waiting in a NOTE column somebody would have to read 939 rows to find.

Measured 2026-11-01, with the population printed beside it, because a count is only as good as the set it counts over:

population: owners go-*,tannevaled — 1789 go.mod seen, 348 kept; set aside:
410 out of scope, 44 in no work tree, 540 published by another project,
0 without a module directive, 0 unreadable
348 modules against floor 1.27.3:  ok=86  BELOW=260  no-go=2
⛔ 262 modules declare a floor below 1.27.3 …
   they live in 221 repositories, so the campaign is about 221 pull requests
   and not 262.
   of those, 262 are PUBLISHED on the proxy (a consumer can install them)
   and 0 were never published.
   and 6 already carry the fix in their working tree but have not been RELEASED…

⛔ Worth saying plainly: the split was added because it might have shrunk the campaign, and it did not — all 262 are installable. A measurement earns its place when either answer would change what you do, not only when it gives the answer you hoped for.

⛔⛔ And the figure this page carried for a day was wrong. It said 904 of 939. That count was true over a population that included 540 modules other projects publish, sitting inside our own work trees: sigs.k8s.io/yaml, cel.dev/expr and twenty more, all inside tannevaled/pantry. Every remote.origin.url said tannevaled, so every one passed the owner test, and nobody here can raise the floor of sigs.k8s.io/yaml. v0.5.0 sets them aside and counts them on the population line. The real campaign is 262 modules.

The counting is a named function rather than four variables inside the printer, so it has a test and needs no network. The test plants all five verdicts — including toolchain, which is not an exposure because it fails closed under GOTOOLCHAIN=local — and asserts that published plus unpublished is the whole exposure, so a row drifting out of both buckets cannot shrink the campaign silently.

A campaign is costed in pull requests, not in findings

⛔ “262 modules below the floor” reads as 262 pieces of work, and it is not: several modules of one repository are raised by one pull request, because the go directives they declare land together. On a sibling campaign 896 stale CI pins turned out to be 123 pull requests — a factor of seven — and an estimate seven times too large is an estimate that gets the campaign refused.

⛔ And the size is not the shape. gopin --gomod --from X --version Y names the version to move exactly — deliberately, because “move anything older” cannot tell a stale pin from a deliberate hold, and this fleet has removed a deliberate one as an outlier before. So a campaign over modules declaring several floors is one run per floor, and v0.7.0 says which:

   they declare 10 different floors, so `gopin --gomod --from X --version
   1.27.3` is 10 runs and not one:
      --from 1.27.1  191      --from 1.26.4    4      --from 1.24      1
      --from 1.27.2   61      --from 1.26.0    1      --from 1.21      1
      --from 1.27.0    3      --from 1.25      1      --from (none)    3
      --from 1.27      3

Two runs cover 252 of the 262. A module with no directive at all is grouped under (none), because --from has nothing to match there. The floors are ordered as Go versions and never as text, since 1.9 is below 1.10 and this list is read by somebody choosing which run to do first.

⛔ Here the pull-request factor is 1.19, not 7: 262 modules in 221 repositories. Said plainly, because it is the second measurement on this page that did not give the answer it was taken for — the first being the published/unpublished split, where all 262 turned out installable. The grouping that saved a sibling campaign seven eighths of its work saves this one nothing much, and 221 pull requests is the real number to decide about.

A module named as a positional argument has no work tree, so there is no repository to credit it to: those are counted apart rather than folded into the estimate, since a module that was not found on disk is one we may not be able to push to at all.

--baseline: a gate for a campaign that cannot be finished in one day

⛔ A report that is red for ever is not a gate. 262 published modules declare a floor below 1.27.3, so modfloor --floor 1.27.3 exits 1 every time it runs and will keep doing so for as long as raising them takes. A lane in that state is read as broken, then ignored — and the day a new module lands below the floor, nothing changes colour.

modfloor --dir … --owners 'go-*' --floor 1.27.3 --write-baseline floor.txt
modfloor --dir … --owners 'go-*' --floor 1.27.3 --baseline floor.txt

--baseline exits 1 only for a module the recorded set does not have. The file is plain text so a tightened baseline has a readable diff, and it names the floor and the mode it was taken against.

RefusedWhy
no floor line, or another floorevery verdict changes the day the floor moves, and it moved three times in four days (1.27.1 → 1.27.2 → 1.27.3). A set of module names says nothing without the floor it was judged against
another mode--offline records what the working trees declare, the default what the proxy serves: different answers about the same modules
--baseline and --write-baselinerecording the answer and then judging it against itself always passes, which is a gate that cannot fail

The file records every module the run measured, clean ones included, and says so with a records all line; a baseline without it (anything v0.6.1 wrote) is refused.

⛔⛔ The clean ones are the point, and the first version left them out. It fired 80 minutes after its own baseline with “8 module(s) are exposed that the baseline did not have” — every one a repository another session had just cloned, one of them appearing on disk a minute before the run, the population growing from 348 modules to 360. A clone arriving is not the fleet getting worse. And the silent half is the dangerous one: with only the exposed set recorded, a module that was ok and is exposed now cannot be told from one never measured, so the real regression would have been filed as population growth and the gate would have passed.

Four outcomes, and only the first fails a run:

WORSEthe baseline measured it and found it clean; it is exposed now. The gate
new to the population (not a regression)exposed, and the baseline never measured it. Work, but nothing says it was ever clean. ⚠ A repository created below the floor arrives this way too, which only a check in its own CI can catch
fixedwas exposed, measured again, no longer exposed
NOT MEASURED THIS TIME (not a fix)was exposed and did not appear at all — clone deleted, renamed, out of the owner globs, or simply not walked. A vanished subject looks exactly like a repaired one to anything that only subtracts two sets, and adding them together is how a campaign declares victory by losing track of its subjects

⭐ The baseline is also what caught the wrong population above. The report prints 348 rows and a summary, and nobody reads 348 rows; the baseline writes the exposed set to a file as a sorted list of module paths, where cel.dev/expr two lines from the top is impossible to miss.

⚠ Where it should run is not settled: a baseline is a statement about one machine’s clone population, so committing one in the repository would make its lane depend on that machine.

modfloor pseudo: dependencies that were never released 

modfloor pseudo [--dir DIR] [--input FILE] [--fleet-prefix PREFIX ...]
modfloor pseudo --dir ~/Documents/VCS/GIT/github.com/go-llmflow/gateway \
  --fleet-prefix github.com/go-volumes/ --fleet-prefix github.com/go-authn/
MODULE                                     VERSION                             FLEET
github.com/go-volumes/interface            v0.0.0-20261026102434-e5b421ad6fae  FLEET
google.golang.org/genproto/googleapis/rpc  v0.0.0-20260928230214-8a89bd6388cc
2 of 120 modules at a pseudo-version, 1 of them the fleet's

It lists every module of a build graph that is required at a pseudo-version, that is at a commit instead of a tag. It reads go list -m -json all, run with GOWORK=off in --dir, or a saved copy given with --input. A replaced module is judged by what is actually built. Modules matching a --fleet-prefix are marked FLEET; without any prefix, every module counts as the fleet’s.

Why it matters. A pseudo-version names a commit that semver says nothing about, and it stays in the module proxy for ever. On 2026-10-26, go-llmflow/gateway depended this way on two fleet modules that had never been tagged.

ExitMeaning
0no fleet module is at a pseudo-version; third-party modules at one are listed but do not fail the check, because their upstream decides whether to tag
1at least one fleet module is at a pseudo-version
2the graph could not be read; a graph with no dependency also exits 2, since it was not measured

The README names its siblings: vulnscan and vulngate for the advisories themselves, gopin for the CI pin, and staletools for installed binaries.
